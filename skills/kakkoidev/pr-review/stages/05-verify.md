# Stage 05: Execution-backed verification

<!-- ICM-TOOLS expect="(Read|Bash|Task)" -->
<!-- ICM-GATE tools="Write" run="test -s ../04-review/output/findings.md" -->

Back the findings with execution: run the changed area's suite, mutation-test the
HIGH-risk findings, confirm any live-metric claims read-only, and adversarially verify
each finding. The gate blocks writing the verification until findings exist.

This is the only stage that touches the filesystem beyond `output/` - and ONLY
inside a throwaway `git worktree` that is removed afterward. The tracked tree is
never modified. Never implement a fix, commit, push, or POST to any live service.

## Inputs
| Source | Location | Scope |
|--------|----------|-------|
| Findings | ../04-review/output/findings.md | what to back with execution + statuses to confirm/refute |
| Checklist audit | ../04-review/output/checklist-audit.md | the checklist items marked `asserted` - the judgment claims this stage must exercise, not trust |
| Runtime evidence | ../03-runtime-evidence/output/runtime-evidence.md | the execution oracle for no-test-oracle (CI/config/IaC) PRs |
| Changed-value impact | ../03-runtime-evidence/output/impact.md | existing tests that assert a value the diff removes - an oracle you must not miss |
| PR repo | the local checkout of `<owner>/<repo>`, if present | to run the suite |

## Process
1. **Detect runner**: package.json `test` / vitest|jest|mocha config / pytest / a `scripts/**/run-all.sh`. If the PR's repo is not checked out locally or no runner is found, write `no runner: static coverage only` for the SUITE line and skip steps 2-3 (do NOT fabricate results) - BUT do not stop there (see step 1b).
   **Third state - a runner exists and is deliberately NOT run** (the operator forbids running this repo's suite locally, CI is the oracle, the environment cannot run it). Never write `no runner` when a runner plainly exists, and never fabricate results. Write `suite not run: <reason>; oracle instead: <what stood in>` for the SUITE line, and with it, all three: (a) the runner you identified and the exact command it would have been, (b) the substitute oracle and what it actually showed (for a CI run: which jobs, which failures, and each failure attributed to this diff or to something else, from evidence not assumption), (c) the named steps that therefore produced NO evidence - 1c worktree, 2 suite, 3 mutation, 3a headline test, 3b probe specs - and which findings are consequently weaker (a finding that would have been probe-proven now rests on source reading plus a failed refutation; say so at the finding, and 7-Point #6 cannot be PASSed on mutation evidence that does not exist).
   **Consult `impact.md` BEFORE writing "no oracle".** If any existing test/snapshot asserts a value this PR removes (a breakage candidate in impact.md), that test IS an oracle for this change - "no oracle / no test for this component" is then FALSE. Trace each candidate: does the assertion or page locator depend on the removed value? If yes it is a latent break (test-coverage finding), even when that suite is `workflow_dispatch`/deploy-only and stays green on the PR pipeline - separate the code-logic claim ("the assertion breaks") from the CI claim ("the pipeline goes red"); assert only the one you verified.
1b. **No-test-oracle PRs (CI / workflow / IaC / config / integration): "execution-backed" does NOT mean static.** A diff with no code test oracle is exactly where the worst misses hide. For such a PR, execution-backing means: the workflow run-history + the real-actor/event instance gathered in stage 03's `runtime-evidence.md`, plus an event/security-context analysis (does the trigger fire for the real actor? does the secret resolve in the store that context uses?). A verification MUST NOT be marked verified for a no-oracle PR on static reads alone - cite the runtime-evidence facts that confirm or refute each mechanism finding. If runtime-evidence genuinely had nothing to show (e.g. brand-new workflow, no history), say so explicitly and mark the relevant findings `UNVERIFIED`, not verified.
1c. **Worktree bootstrap (the expensive step - do it ONCE, then reuse for suite + mutation + probes).** `git worktree add <abs-run-dir>/work/<name> HEAD` places the throwaway worktree under the run's `work/` dir so a session restart does NOT delete it mid-run (never the harness scratchpad - a restart there costs a full rebuild). `git worktree add` alone is the easy 5%; for a real monorepo whose PR head sits on a moved master the deps/codegen do NOT carry over the gap: (1) `pnpm install --prefer-offline` (or the repo's manager) - never assume node_modules symlinks suffice across a base-branch gap; (2) run the codegen the repo needs when its inputs differ from the tracked tree (`prisma generate`, openapi) - a stale client references models that no longer exist or misses new ones; (3) secrets: SYMLINK env files (`ln -s`), never read or copy their contents (a hook rightly blocks reading `.env` - symlink, respect it); (4) if jest-setup migrates a SHARED local test DB forward, DISCLOSE that mutation in verification.md; (5) before trusting a `@workspace`-style package that resolves through a relative symlink into the original tree, verify its diff is irrelevant to the change. Remove the worktree with `git worktree remove --force` before the run's `work/` is cleaned, or git leaves a stale registration.
2. **Suite**: in the bootstrapped worktree, run the changed area's tests; record total / passed / failed / skipped.
3. **Mutation** (HIGH-risk findings + questioned symbols only), in the bootstrapped worktree (1c) - the tracked tree is never modified:
   - inject ONE representative fault (flip a condition, drop a guard, change the constant).
   - Run the suite. RED = caught (good). GREEN = the fault SURVIVED -> behavior untested -> finding + 7-Point #6 FAIL.
   - Revert the fault between mutations; `git worktree remove --force` when the stage is done (even on error).
3a. **Headline-test revert check (MANDATORY, regardless of severity or of any finding).** Identify the test(s) the PR adds or changes for its headline bug or behavior - the one the PR body or ticket names as proof. In the bootstrapped worktree, run it against the PR head AND against the parent commit's version of the non-test files (keep the new test, revert the fix). It MUST fail on the parent: a headline test that passes on pre-fix code cannot detect the bug it claims to cover - that is a test-coverage finding and 7-Point #6 FAIL. Record `headline-test: <spec> head=<pass|fail> parent=<pass|fail>`. A PR with no headline test records `headline-test: none added` (a finding when the PR fixes a bug); a run where 1c could not bootstrap records `headline-test: not run: <why>`, never a pass.
3b. **Probe specs (for any finding whose failure scenario is constructible with the repo's test harness - MANDATORY for CRITICAL/HIGH, and equally mandatory at any severity for a finding you intend to report as a judgment call for the author to decide).** In the bootstrapped worktree, write a disposable probe spec that exercises the failure, and run it against BOTH the PR head AND the reverted code (checkout the pre-PR state of the touched files). The two-direction result distinguishes a NEW regression (fails on head, passes on revert) from a PRE-EXISTING issue (fails on both). Probes NEVER ship to the PR branch; record each probe's fixture + assertion in verification.md as a ready-made regression spec. A CRITICAL confirmed by a two-direction probe is execution-proven, not merely source-confirmed - the strongest evidence this stage can produce.
   **Severity is the wrong gate for a decision.** Do not skip the probe because a finding scored LOW: severity is often exactly what the probe settles, and a LOW handed to the author as "decide whether this matters" is a guess dressed as a decision unless it carries a measured result and a ready-made regression spec. A LOW finding probed anyway, with a measured result pair plus a fails-on-base result, reaches the author as an actionable choice rather than a hypothesis. If the probe is genuinely too expensive to construct, say so in the finding - never present an unprobed judgment call as settled.
4. **Live (read-only MCP)**: for any phantom-metric finding, confirm the metric/log exists (Datadog/Sentry read-only). A dashboard referencing a never-emitted metric is HIGH.
5. **Adversarial per-finding verify (MANDATORY).** For each CRITICAL/HIGH finding from stage 04, run an INDEPENDENT pass that tries to REFUTE it against source/runtime-evidence (not to confirm it).

   **`REFUTED` requires positive contradicting evidence. Absence of confirmation is `UNVERIFIABLE`, not `REFUTED`.** These two were collapsed here until 2026-09-16 ("default to refuted if the evidence is not actually there"), and that collapse is the exact failure `alibaba/open-code-review` names: a correct finding destroyed silently because nobody could prove it, with nobody learning it was dropped. Resolve each finding to one of FOUR states, not three:
   - `CONFIRMED` - evidence positively establishes it (source citation or execution token).
   - `REFUTED` - evidence positively contradicts it. Their two grounds are the bar, and both are literal rather than inferential: **Ground A**, the code the finding describes is absent from the subject file's diff; **Ground B**, one diff line literally contradicts the finding's central claim with no chain of reasoning in between. A refutation that needs a chain of reasoning is not a refutation.
   - `PLAUSIBLE` - evidence is consistent with it but does not settle it.
   - `UNVERIFIABLE` - the evidence needed is not reachable in this run (walled-off requirement, no runner, needs a live service). Record WHAT was unreachable. `UNVERIFIABLE` is a truth state, never a disposition: it carries to the value gate as `report-only(unverified)` at minimum, and a diff-introduced correctness/security/data-loss finding that is merely `UNVERIFIABLE` still posts `inline`.

   **Protected subjects - the verifier does not get to be confident** (their pre-correctness veto list, `review_filter_task_user.md`, adapted): memory and resource lifetime, concurrency and ordering, linkage and declaration consistency, behavioural or compatibility change, unused or silently-ignored parameters. On these subjects a finding may NOT be resolved `REFUTED` by reasoning alone - it needs Ground A or Ground B, or it stays `PLAUSIBLE`. Reasoning yourself out of a concurrency finding is the cheapest way this stage produces a false negative.

   **The verifier must not share the finder's context.** Where the runtime permits, spawn the refutation as a SEPARATE pass carrying the diff, the finding text, and nothing else - deliberately LESS context than the finder had. Ours has historically been the same model in the same run holding the same context that produced the finding, which makes it a consistency check dressed as an independent one; theirs is a fresh call with a one-directional mandate, and is better calibrated against a reviewer talking itself out of a real finding. If a separate pass is genuinely unavailable, say so in verification.md rather than claiming independence. Resolve each to a final `CONFIRMED` / `PLAUSIBLE` / `REFUTED` / `UNVERIFIABLE` + the evidence that settled it. For HIGH-stakes diffs (auth/secrets/CI-triggers/payment/migrations, or actor/event/environment-conditional behavior) use perspective-diverse verifiers (correctness / security / does-it-actually-execute) via parallel Task, not one. This is the second pass that makes a finding "done"; a finding that survives a genuine refutation attempt is real, one that is positively contradicted (Ground A or Ground B) is dropped with the reason recorded, and one that merely cannot be settled is downgraded to `PLAUSIBLE` or `UNVERIFIABLE` - never dropped for lack of proof.
6. **Exercise the `asserted` checklist items (MANDATORY when checklist-audit.md has any).** Every `asserted` MET from stage 04 is an unverified judgment until exercised here - promote it to `verified` only after you actually do the thing the item claims, or downgrade it to `GAP`. Never let a proxy stand in: "documentation sufficient / understandable without context" -> READ the changed/added doc content end to end (not the diffstat), and say whether a newcomer could act on it; "enough test coverage *for the risk*" -> inspect the tests that cover the changed logic and name which branches/edge-cases of the new code are and are NOT exercised (a count is not coverage); "observability / failures easily debugged" -> look at the actual error/log/output surface the change emits and state what a failure would show; "no secrets" -> grep the diff; "deps up-to-date" / "env-var config" -> diff the manifest / grep for `process.env`. Record each as `verified: <what you did + result>` or `GAP: <what the exercise showed>`. If exercising is impossible here (needs a running service, human judgment), mark it `UNVERIFIED: <why>` - never silently `verified`. Then re-run the stage-04 **bias alarm** against the exercised results: if the gaps still cluster only on the scannable items, look harder at the ones you passed.
7. **Per-finding value/judgment pass (MANDATORY - the noise gate).** Distinct from step 5: that pass asks IS IT TRUE, this pass asks IS IT WORTH THE AUTHOR'S TIME - do not merge them (a TRUE finding can still waste the reviewer's time). For EVERY finding, re-articulate it from scratch, one last time, in one plain sentence - forcing the re-articulation is what surfaces "this is pre-existing / out of scope / wouldn't change the merge decision". Then answer, per finding: Would a senior engineer bother writing this comment on this PR? Does it change whether the PR should merge? Is it introduced by this diff, or pre-existing? Is it in scope for the PR's stated goal? Can it be said in ONE concise sentence in natural engineer language? Resolve stage 04's `proposed:` to a final disposition line in verification.md:
   ```
   Disposition: F<n> final: inline | report-only(<reason>) | dropped(<reason>) - <one-line justification>
   ```
   A finding posts `inline` only if it clears stage 04's objective floor AND this judgment gate. **Asymmetry (guardrail):** demote only for the explicit reasons (`pre-existing`, `out-of-scope`, `style`, `LOW-not-merge-changing`) - an `introduced-by-diff=sibling` finding is never demoted as `pre-existing`, it is the same defect class the PR claims to fix; NEVER demote a diff-introduced correctness/security/data-loss finding; ties resolve to `inline` - when in doubt, POST. A floor-passing finding that fails only the one-sentence test is DISTILLED into one sentence, not demoted. `dropped` is only for findings the re-articulation showed to be wrong/vacuous, always with the reason. Every `F<n>` in findings.md gets exactly one Disposition line - report-only is a recorded destination, not a silent drop.

   **Check the fix shape too (the fix is part of the finding).** Re-read each finding's `Fix shape:` line from stage 04: does the suggested fix patch one instance or change a contract, and what does it do to existing callers already promised success? A suggested fix that drops work other callers depend on (clears a shared queue, rejects requests already acknowledged, removes a fallback a sibling path uses) is itself a defect: rewrite the fix before it posts, and if the PR's OWN fix has that shape, that is a finding in its own right. A true finding with a wrong-shape fix costs the author a full review round.

   **Cross-check the self-graded claims (deterministic).** The floor is written by the same pass that wants to post the finding - do not let it grade itself unchecked. Run:
   ```bash
   bash ~/.agents/skills/kakkoidev/pr-review/tools/check-value-claims \
     ../04-review/output/findings.md ../01-context/output/pr.diff > output/value-claims.tsv
   ```
   Every `SUSPECT` row MUST be resolved before this stage completes: either ground the `introduced-by-diff=yes` (or `=sibling`) claim by citing the actual changed file in the finding block - for a sibling, the fix site it shares the defect class with - (then re-run the tool), or concede the claim is wrong - flip it to `=no` in findings.md and demote the disposition accordingly. A final `value-claims.tsv` still carrying a SUSPECT fails the held-out check. (The tool catches lazy claims - no cited file in the diff; it cannot catch a pre-existing pattern cited next to a changed file, so the judgment questions above still apply.)
